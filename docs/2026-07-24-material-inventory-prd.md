# PRD — 자재소모 재고관리 재설계 (소모 요청 · 담당자 승인 · 감산)

| 항목 | 내용 |
|------|------|
| 문서명 | 성능기골 스티커 보드 — 자재소모 페이지 재설계 (재고 + 소모요청/승인) |
| 버전 | v1.0 |
| 작성일 | 2026-07-24 |
| 대상 파일 | `remove_list.html` |
| 인프라 | Firebase Realtime Database, Spark(무료), 서버 없음 |
| 선행 | 인증 개편 v1.1(부관리자 역할, `users/{id}/materialAdmin`) |
| 상태 | 구현·배포 완료 |

---

## 1. 배경 · 방향 전환

기존 `remove_list.html`은 "소모할 때마다 1건씩 로그로 쌓는" 방식이었다(누구나 입력·삭제, 로그인 미강제). 이를 **재고(Stock) 중심 + 소모요청/승인 워크플로우**로 전환한다.

- 관리자/부관리자가 **재고 마스터(항목 + 전체수량)** 를 관리한다.
- 소모자는 **"소모" 버튼을 1회씩** 눌러 **대기 소모수량**을 쌓는다(재고 즉시 차감 안 함).
- **담당자(관리자/자재소모 부관리자)가 확인 후 삭제**하면 그 수량만큼 **전체수량에서 감산**한다.

## 2. 목표 / 비목표

### 목표
1. 항목별 **전체수량(재고)** 을 표로 표시.
2. 소모자는 **소모 +1 / 취소 −1**(본인 대기분)로 소모수량을 쌓는다.
3. 담당자가 **작업자별 대기 소모를 확인·감산**한다.
4. 재고 마스터 입력·수정·삭제는 **관리자/자재소모 부관리자만**.
5. 로그인 강제 · 감사 로그 · 저재고 표시.
6. Spark(무료) · **Firebase 규칙 변경 없이** 동작.

### 비목표
1. 발주/입고 자동화, 바코드, 외부 연동 없음.
2. 서버·유료 요금제 없음.
3. 기존 소모 로그(구 push-id 레코드)의 마이그레이션 없음(보관만).

## 3. 역할 · 권한

| 역할 | 권한 |
|------|------|
| 소모자(로그인 사용자 전원) | 소모 +1 / 본인 대기분 취소 −1 |
| 담당자 = 관리자(`admin`) 또는 자재소모 부관리자(`materialAdmin`) | 위 + 재고 항목 추가/수정/삭제 + 작업자별 대기 소모 확인·감산(및 반려) |

- 판정: `canManage = (username === 'admin') || (users/{username}.materialAdmin === true)` — 인증 v1.1과 동일 패턴.
- **로그인 강제**: 진입 시 `localStorage.username` 없으면 `auth.html`로 리다이렉트.

## 4. 데이터 모델 (기존 `materialConsumption` 경로 하위 → 규칙 변경 불필요)

```
materialConsumption/
  items/{itemId}/                 # 재고 마스터 (담당자 입력)
    seq        : number           # 순번(정렬/표시용)
    stockNo    : string           # 재고번호
    partNo     : string           # 파트넘버
    qty        : number           # 전체수량(현재고, ≥ 0)
    unit       : string?          # 단위(선택)
    createdAt  : number
    createdBy  : string
  requests/{itemId}/{workerId}/   # 대기 소모 (작업자별 누적)
    count      : number           # 이 작업자의 대기 소모수량(> 0)
    updatedAt  : number
  history/{pushId}/               # 승인(감산)된 소모 이력 → 스파크라인·리포트·감사
    itemId, stockNo, partNo, worker, qty, approver, timestamp
  (기존 push-id 소모 레코드 = 보관용 잔존, 새 페이지는 무시)
```

- `items`/`requests`/`history` 각각에 실시간 리스너(onValue)를 걸어 변경 시 재렌더. 구 아카이브 레코드는 읽지 않음.

## 5. 화면 (기존 산업용 다크 테마 유지)

**표 컬럼**

| 순번 | 재고번호 | 파트넘버 | 전체수량 | 대기소모 수량 | 소모 | (담당자) 관리 |
|------|----------|----------|----------|----------------|------|----------------|
| seq | stockNo | partNo | qty (저재고 강조) | 대기 합계 + **스파크라인** | [소모 +1] / [취소 −1] | 작업자별 [확인·감산]/[반려] · [재고수정] · [삭제] |

- **대기소모 수량 스파크라인**: 해당 항목의 **최근 승인 소모 이력**(history)을 인라인 SVG로 그린 미니 추이 그래프. 외부 라이브러리 없음(CSP/GitHub Pages 안전). 이력이 없으면 "—".
- **저재고 표시**: `qty ≤ LOW_STOCK(=3)` 이면 전체수량 셀/행을 경고색으로 강조. **전 항목 공통 기준 3개.**
- **소모 열**: 소모자는 [소모] 버튼, 본인 대기분이 있으면 수량과 [취소] 노출.
- **담당자 관리 열**(canManage 일 때만): 항목별 작업자 대기 목록(누가 몇 개)과 각 건 [확인·감산]/[반려], 그리고 [재고수정]·[삭제]. 상단에 [+ 항목 추가] 폼.

## 6. 워크플로우 · 규칙

### 6.1 소모(+1) / 취소(−1) — 소모자
- [소모]: `requests/{itemId}/{myId}.count` 를 **원자적 증가**(트랜잭션/`increment`). 재고는 건드리지 않음.
- [취소]: 본인 `count` 를 −1, 0이 되면 노드 삭제. **담당자 확인 전까지만** 가능(본인 것만).

### 6.2 확인·감산 — 담당자
- 대상 `requests/{itemId}/{worker}.count = c` 확인.
- **감산(트랜잭션)**: `items/{itemId}.qty = max(0, qty − c)` — 음수 방지(재고보다 크면 0으로 클램프하고 경고).
- `requests/{itemId}/{worker}` 삭제, `history` 에 1건 push, 로그 `MATERIAL_CONFIRM` 기록.

### 6.3 반려 — 담당자(추가 검토안)
- 잘못 쌓인 대기건을 **감산 없이** 삭제. 로그 `MATERIAL_REJECT`.

### 6.4 재고 관리 — 담당자
- 추가: 재고번호·파트넘버·전체수량(+단위) 입력 → `items` push(seq 자동). 로그 `MATERIAL_ADD_ITEM`.
- 수정: 전체수량 재설정(입고/보정). 로그 `MATERIAL_EDIT_STOCK`.
- 삭제: `items/{itemId}` + `requests/{itemId}` 제거. 로그 `MATERIAL_DELETE_ITEM`.

## 7. 동시성 · 정합성 (추가 검토)

- **원자적 증감**: 다중 사용자·연타에 의한 경쟁을 피하기 위해 소모/취소/감산은 트랜잭션(또는 `increment`)으로 처리.
- **음수 재고 방지**: 감산은 `max(0, …)` 클램프. 감산량 > 재고면 담당자에게 경고.
- **감산 시점 기준**: 감산은 승인 순간의 최신 `qty` 기준(트랜잭션) → 입고·수정과 경쟁해도 안전.

## 8. 보안 수준 (기존과 동일)

- 권한 검사는 **앱 레벨**(보드·사역표와 동일 "신뢰 내부팀" 수준). `materialConsumption` 규칙은 개방 유지 → 콘솔 직접 조작까지는 막지 않음.
- 서버가 없어 "담당자만 감산"을 암호학적으로 강제하진 않음(앱 레벨 가드).

## 9. 인수 조건

- [ ] 미로그인 시 `auth.html`로 이동.
- [ ] 표에 순번·재고번호·파트넘버·전체수량·대기소모(스파크라인)·소모·(담당자)관리 열 표시.
- [ ] 소모자가 [소모]로 대기수량 누적, [취소]로 본인 대기분 −1.
- [ ] 담당자가 [확인·감산] 시 전체수량이 그만큼 감소, 대기건 삭제, 이력·로그 기록.
- [ ] `qty ≤ 3` 항목은 저재고로 강조(전 항목 공통).
- [ ] 담당자만 항목 추가/수정/삭제·확인·감산 가능(일반 사용자는 불가).
- [ ] Firebase 규칙 변경 없이 동작.

## 10. 향후 과제

- 저재고 자동 알림(푸시/메일)은 서버 필요 → 보류.
- 입고/발주 관리, 월별 소모 리포트 상세화는 후속.

## 부록 — 참고: 원자적 증가(클라이언트)

```js
import { runTransaction } from "firebase/database";
// 소모 +1
await runTransaction(ref(db, `materialConsumption/requests/${itemId}/${myId}`),
  n => ({ count: ((n && n.count) || 0) + 1, updatedAt: Date.now() }));
// 취소 -1 (0이면 삭제)
await runTransaction(ref(db, `materialConsumption/requests/${itemId}/${myId}`),
  n => { if (!n) return n; const c = (n.count || 0) - 1; return c > 0 ? { count: c, updatedAt: Date.now() } : null; });
```
